[根拠とUDP送信の実測](udp-sender.md)を参照。UDP送信まで実装済みで、以下は初期診断の記録。

Windowsレジストリ: DisplayVersion 25H2、CurrentBuild 26200、UBR 9168。
Rust 1.95.0 x86_64-pc-windows-msvc、releaseビルド、MMCSS Pro Audio成功。

## 確認できたこと

- 現在の既定マルチメディア出力は **スピーカー (2- VB-Audio Virtual Cable)**。
- 両測定で48,000Hz・2ch・float32のネイティブミックス形式を使用。SRCなし。
- 仮想ケーブルではIAudioClient3の共有最小周期128フレーム（2.667ms）が広告される。
  しかし `InitializeSharedAudioStream(LOOPBACK | EVENTCALLBACK, 128, ...)` は
  `0x88890021 / AUDCLNT_E_INVALID_STREAM_FLAG` を返した。
- 物理Realtekの共有最小/既定/最大周期はすべて480フレーム（10ms）。
  480フレームで同じIAudioClient3初期化を試しても同じエラーになった。
- どちらも新しいIAudioClientを使う通常のイベント駆動ループバックへフォールバックできた。
  最小周期が「問い合わせ可能」なことと「ループバックで使用可能」なことは別だった。
- デバイス最小周期（仮想ケーブル2ms / Realtek3ms）は共有エンジン最小周期ではない。
  それを実測キャプチャ周期として表示しない。

## 測定条件

各180秒。`--backend auto --test-tone`、同じ440Hz・振幅0.005の内蔵テスト信号。
測定は順番に行い、キャプチャ本体のビルド・テストは測定外で実行した。
既定デバイスやマスター音量は変更せず、RealtekはIDで指定した。
本プログラム以外のシステム負荷・他アプリの再生は制御していないため、厳密に隔離した
音源/負荷比較ではない。テスト信号はキャプチャ開始後に別スレッドで再生を開始する。

```powershell
.\target\release\sender-windows.exe --backend auto --seconds 180 --test-tone --output runs\vb-auto-180s.jsonl
.\target\release\sender-windows.exe --backend auto --device '{0.0.0.00000000}.{07dce926-d0c4-42c5-810f-6dd7c0408d89}' --seconds 180 --test-tone --output runs\realtek-auto-180s.jsonl
```

通知間隔は仮想ケーブルより揃うが、ドライバ時刻に基づく先頭サンプル経過時間は長い。
不連続は開始直後だけではなく約68.88秒地点でも1回発生した。欠落27フレームは
デバイス位置からの観測であり、原因を特定したり、単純にアプリのオーバーランと断定したりしない。
この測定から「Realtekなら低遅延・完全安定」と結論づけることはできない。

## 解釈と次の判定

この測定範囲では約500ms分のキャプチャまとめ取りは再現していない。
ただし過去の別実装、HDMI/プロジェクター出力、別の負荷条件での現象まで否定するものではない。
音声タイミングを隠すアプリケーションバッファは導入していない。

先頭サンプルの時刻はWASAPI/ドライバ由来の推定で、物理出力までの遅延ではない。
USB/RME、LAN、macOSの出力は未測定。**20ms/10msのend-to-end目標達成は宣言しない。**
キャプチャ内のマイクロ秒単位の処理より、音声が取得可能になるまでの周期・経過時間を
先に改善すべき、というのが今回の観測に基づく判断。

現時点で動作確認済みの基準は通常のendpoint loopback。これはproduction最速バックエンドの
選定ではない。process loopback / PRE-VOLUME・PRE-MUTE / HDMIエンドポイントでの比較は未完了。
低周期の共有レンダーストリームを併設してエンジン周期を要求する方式も未試験。
これらを調べてからUDP localhost検証へ進む。
